\section{Introduction}
\label{sec:intro}
GPU performance engineering is expert work. Getting a kernel to run faster requires reasoning about the
memory hierarchy, warp scheduling, occupancy and instruction-level behaviour at the same time, and
expert tuners routinely spend weeks on a single kernel. Large language models can attempt the same edit
in seconds, which raises an obvious question: how much of that expertise can be supplied through the
prompt, and how much of the resulting speedup survives contact with a real application?

Existing code benchmarks do not answer this. HumanEval-style suites \cite{chen2021codex} and
repository-level issue resolution \cite{jimenez2024swebench} score functional correctness, not
execution time, and recent GPU-specific benchmarks \cite{ouyang2025kernelbench,nichols2024parallel}
evaluate standalone kernels written from a reference implementation rather than edits to code that a
scientific application already depends on. Meanwhile, the first thing a human expert looks at---profiler
output---is exactly the kind of context an LLM never sees by default.

This paper studies an end-to-end loop that closes that gap: profile the application, summarize the
profile into the prompt, ask the model for an optimized version of one source file, build it, verify it
against the application's own notion of correctness, measure it, and feed failures back for a bounded
number of repair iterations. Within this loop we treat the prompt as the object of study.
% NEW (2026-10-29): plain definition of gaming, asked for in review.
One behaviour needs a name before we go further. A model that is asked for speed and checked only by
the program's output can satisfy both by removing the work the program exists to measure: a
benchmark that times a loop of atomic operations still prints the right total if the loop is replaced
by one addition of the pre-computed sum. We call such an edit \emph{benchmark gaming}. It is not a
model error in the usual sense, since the output is correct and the program's own check passes; it is a
mismatch between what was asked for and what was meant, and it makes the reported speedup
meaningless.
% NEW (written for the TOMPECS version; not in the original paper)
Because the loop's output is a measured execution time, the study is as much about how such systems
must be \emph{evaluated} as about how they should be prompted. We organize it around five research
questions:
\begin{description}\itemsep2pt
\item[RQ1] Which components of the prompt matter, and how reliably? (Section~\ref{sec:prompts})
\item[RQ2] Can speedups reported on benchmarks be trusted, and what does a model do when the
  benchmark's own scaffolding can be deleted? (Section~\ref{sec:intent})
\item[RQ3] Do conclusions drawn on single-kernel benchmarks transfer to the production applications
  those kernels represent? (Section~\ref{sec:realapps})
\item[RQ4] What is profiling evidence worth, supplied raw and supplied interpreted?
  (Sections~\ref{sec:profabl} and~\ref{sec:guidvar})
\item[RQ5] What measurement and validation practice is needed to report any of this credibly on shared
  hardware? (Sections~\ref{sec:timing}, \ref{sec:pitfalls} and~\ref{sec:limits})
\end{description}
Our contributions are:

% successes, slowest-valid counts) so that each claim names a measurable effect.

\begin{itemize}\itemsep2pt
\item \textbf{A prompt-component ablation} over six variants, two models and six HeCBench kernels
  ($72$ runs, Section~\ref{sec:prompts}). The instruction block decides how often a model returns a
  valid candidate at the first attempt: $11$ of $12$ runs when only the prohibitions are removed,
  $8$ of $12$ when the requirement to argue correctness is removed. Removing that requirement is also
  what lets one model game a benchmark. Stripping the instructions to one sentence gives GPT-5 its
  slowest valid result on four of five benchmarks, by $31$--$34\%$ on two of them; a ``think step by
  step'' instruction never gives either model its slowest result but fails outright twice.
\item \textbf{A semantic-preservation constraint} that stops benchmark gaming
  (Section~\ref{sec:intent}). Without it, both models delete the atomic loop a benchmark exists to
  measure and report $1504\times$ and $2809\times$ while output and the built-in check are unchanged;
  with it, both return honest, roughly neutral results. We also give the detection rule we use, since
  neither output comparison nor the benchmark's own check can catch this class of edit.
\item \textbf{An end-to-end evaluation on two production applications}, AutoDock-GPU and Cholla
  (Section~\ref{sec:realapps}), each with a correctness gate derived from its scientific output and
  validated by fault injection. On Cholla all four model outputs under the baseline prompt (two
  independent samples per model, $1.476$--$1.584\times$) beat our expert hand-tuned reference
  ($1.468\times$); on AutoDock-GPU no model or prompt found the restructuring that is worth
  $1.532\times$ by hand.
\item \textbf{A profile-data ablation} (Section~\ref{sec:profabl}) that isolates the contribution of
  PC-sampling and roofline data by removing it from an otherwise identical prompt. Profiling data is
  worth $7.7$--$11.5\%$ on the large application; on single-kernel benchmarks it moves individual
  results in both directions with no net gain (geometric mean $0.98$--$1.00$ per model).
\item \textbf{A measurement of what happens when profiling data is made prescriptive}
  (Section~\ref{sec:guidvar}). Converting metrics into a checklist of named remedies produces both our
  largest gain ($1.00\times \to 1.38\times$ on \texttt{bincount}) and our largest loss
  ($0.84\times \to 0.35\times$ on \texttt{concat}, where the model applied a named remedy literally),
  at repetition spreads below $5\%$. Interpretation widens the spread of outcomes rather than shifting
  its centre, which a mean speedup hides.
\item \textbf{Problems that appear only on real code} (Section~\ref{sec:pitfalls}): the model cannot see
  how its file is compiled, so it redefines symbols that another file already includes and changes a
  signature that ten call sites depend on; an application aborts with a bare assertion and throws away
  the error message the repair loop needed; and timings on a shared machine silently change by tens of
  percent between sessions unless contention is detected per repetition.
\end{itemize}

Taken together, the results argue that prompt design is a first-order lever for turning general-purpose
code models into usable performance tools---but also that conclusions drawn on single-kernel benchmarks
do not automatically transfer to the applications those kernels are meant to represent.

\paragraph{Organization.}
